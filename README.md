# Local-RAG

홈랩과 인프라 코드에 대해 로컬 LLM 으로 질문하는 RAG 파이프라인.

외부로 나가는 데이터가 없다. 임베딩과 생성 모두 맥북(Mac M3)의 Ollama 를
쓰고, 벡터 저장소도 이 디렉토리 안에 있다.

## 왜 만들었나

홈랩이 커지면서 "이거 왜 이렇게 해놨더라" 를 찾는 데 시간이 걸리기
시작했다. 레포 다섯 곳에 흩어진 매니페스트와 tf 파일, 그리고 커밋
메시지를 사람이 grep 으로 뒤지는 대신 물어보고 싶었다.

## 구조

세 단계로 나뉜다. 각 단계는 따로 다시 돌릴 수 있다.

```
collect_docs.py   원본 → data/ 로 복사 + manifest.json
      ↓
build_index.py    카테고리별 청킹 → 임베딩 → chroma_db/
      ↓
query.py          검색 → 컨텍스트 조립 → 생성
```

### collect_docs.py

원본을 그대로 두고 `data/` 에 복사본을 만든다. 이유가 두 가지다.

무엇이 인덱스에 들어갔는지 한눈에 보이게 하려는 것이 하나다. `data/` 를
열어보면 끝이다.

다른 하나가 더 중요하다. **RAG 에는 문서 단위 권한이 없다.** 한 번
인덱스에 들어간 내용은 그 인덱스를 질의할 수 있는 누구에게나 노출된다.
그래서 "넣지 않는 것" 이 유일한 통제 수단이고, 그 결정을 이 파일 한 곳에
모아 뒀다. 무엇을 왜 뺐는지도 주석으로 남아 있다.

시크릿은 두 겹으로 막는다. 경로 제외 패턴(`terraform.tfvars` 등)이 첫
겹이고, 파일 내용에서 실제 값이 박힌 시크릿을 찾아내는 정규식이 둘째
겹이다. 참조 표현(`secretKeyRef`, `os.environ`, `var.foo`)은 값이 아니므로
걸리지 않게 해 뒀다.

### 카테고리

파일마다 `category` 를 붙인다. 종류마다 잘라야 하는 방식이 다르기
때문이다.

| category | 대상 | 자르는 기준 |
|---|---|---|
| `docs` | `.md` | 마크다운 헤더 |
| `infra-code` | `.tf` `.yml` `.sh` `Dockerfile` | `resource` / `module` / YAML 문서 경계 |
| `app-code` | `.py` `.html` | 함수·클래스 경계 |
| `history` | git 커밋 로그 | 커밋 하나 = 청크 하나 |
| `context` | `~/.claude` 메모 | 마크다운 헤더 |

같은 크기로 일괄해서 자르면 셋 다 망가진다. tf 파일을 1500 자로 뭉텅
자르면 리소스 블록 중간이 잘려 "이게 무슨 리소스였는지" 가 청크에서
사라진다.

### git 커밋 로그를 넣는 이유

코드는 현재 상태만 보여준다. **왜 그렇게 했는지, 무엇을 하지 않기로
했는지는 커밋 메시지에만 남는다.**

실제로 효과가 확인됐다. "traefik access log 를 왜 파일이 아니라 stdout
으로 내보냈나" 라는 질문에 "파일로 쓰면 봇 스캔이 몰릴 때 19G 노드
디스크가 찬다" 는 판단 근거가 나왔는데, 이 문장은 어느 코드 파일에도
없고 커밋 메시지에만 있었다.

커밋 제목을 `##` 로 뽑는 것이 핵심이다. 헤더 분할기가 그 경계에서
자르므로 청크가 커밋 단위로 딱 떨어진다. 변경 파일 목록도 함께 넣어서
파일명이 검색 표면이 되게 했다.

### breadcrumb 주입

청크 본문 맨 앞에 출처 경로를 붙인 뒤 임베딩한다.

```
azure-standard/network.md > 아키텍처 > 네트워크 > NSG 규칙

### NSG 규칙
아웃바운드는 명시 요청 없으면 추가하지 않는다.
```

이게 검색 품질에 제일 크게 작용한다. breadcrumb 이 없으면 저 청크의
벡터 안에는 "어느 프로젝트의" "무슨" NSG 인지가 전혀 없다. 조상 헤더와
파일 경로를 붙여 두면 그 단어들이 벡터에 들어간다.

**헤더 깊이는 중요도가 아니라 구체성이다.** `###` 가 `##` 보다 덜 중요한
게 아니라 범위가 더 좁을 뿐이고, 질문도 대개 구체적이라 깊은 청크가
정답인 경우가 많다. 그래서 `depth` 는 메타데이터로 남기되 점수에는 쓰지
않는다. 깊이로 감점하면 오히려 손해다.

## 모델

| 용도 | 모델 | 왜 |
|---|---|---|
| 임베딩 | `bge-m3` | 문서도 커밋도 전부 한국어다. 영어 중심인 `nomic-embed-text` 로는 잘 안 걸린다. 컨텍스트 8192 라 긴 커밋 본문도 안 잘린다 |
| 생성 | `qwen2.5:14b` | 한국어가 자연스럽고, "주어진 문서에만 근거하라" 는 제약을 `llama3.1` 보다 잘 지킨다 |

RAG 에서는 유창한 쪽보다 지어내지 않는 쪽이 중요하다.

둘 다 환경변수로 바꿀 수 있다. 생성 모델만 바꾸는 것은 공짜지만,
**임베딩 모델을 바꾸면 인덱스를 다시 만들어야 한다.**

```bash
RAG_LLM=qwen2.5:latest python query.py "..."     # 7B, 대략 두 배 빠름
```

## 쓰는 법

환경은 uv 로 잡는다. `uv.lock` 을 커밋해 두어서 어느 기계에서든 같은
버전 조합이 선다.

```bash
uv sync                    # .venv 생성 + 의존성 설치 (4 초)
```

apt 의 `python3-venv` 는 필요 없다. uv 가 가상환경도 파이썬 자체도
직접 관리한다.

```bash
uv run collect_docs.py     # 원본 → data/
uv run build_index.py      # data/ → chroma_db/ (바뀐 문서만)
uv run query.py "hermes 가 왜 안 뜨나"
```

`build_index.py` 는 두 번째 실행부터 바뀐 문서만 다시 임베딩한다. 파일
내용의 sha256 을 청크 메타데이터(`doc_hash`)에 같이 넣어 두고, 다음
실행 때 현재 해시와 비교한다. 해시를 별도 상태 파일이 아니라 인덱스
안에 두는 이유는, 상태 파일은 인덱스와 따로 놀다 어긋나고 나중에
Chroma 를 k3s 로 옮길 때 따라가지도 않기 때문이다.

전부 그대로면 2.6 초에 끝나고 임베딩을 아예 건너뛴다. 문서 하나가
바뀌면 그 문서의 옛 청크만 지우고 다시 넣는다(3.6 초). 새로 넣기만
하면 청크 경계가 달라졌을 때 옛 청크가 남아 계속 검색에 걸린다.

```bash
python build_index.py --full      # 통째로 다시 만든다
```

`--full` 이 필요한 경우는 두 가지다. **청킹 규칙을 고쳤을 때** — 파일은
안 바뀌었으니 해시도 같아서 증분으로는 반영되지 않는다. 그리고
**임베딩 모델을 바꿨을 때** — 이건 `--full` 없이도 자동으로 감지한다.
청크에 `embed_model` 을 같이 남겨 두어서, 다르면 컬렉션을 버리고 다시
만든다. 차원도 의미도 안 맞는 벡터가 섞이면 검색이 조용히 이상해진다.

빈 파일은 건너뛴다. 청크가 0 개라 인덱스에 흔적이 안 남고, 그러면 매
실행마다 "새 문서" 로 잡혀 "바뀐 것 없음" 판정이 영영 나오지 않는다.
`azure-standard` 의 빈 `outputs.tf` 2 개가 실제로 그랬다.

질의 옵션:

```bash
python query.py -c history "NSG 아웃바운드 정책"   # 커밋 이력에서만
python query.py -k 10 "..."                        # 근거를 더 많이 (기본 6)
python query.py -s wizparking "..."                # 특정 레포에서만
python query.py --show "..."                       # 검색된 청크 원문 출력
```

카테고리 필터가 있는 이유는 질문 종류가 갈리기 때문이다. "왜 이렇게
했지" 는 `history` 와 `docs` 에 답이 있고 "그 값이 뭐지" 는 `infra-code`
에 있다. 섞어서 검색하면 서로를 밀어낸다.

## 성능

2026-08-13 dev-01(LXC, 2 vCPU / 4GB) 실측. 문서 187 개 → 청크 910 개
(인덱스 13MB).

| 단계 | 시간 |
|---|---|
| 수집 (`collect_docs.py`) | 0.7 초 |
| 전체 인덱싱 | 61 초 (그중 dev-01 CPU 는 6.2 초) |
| 증분 인덱싱 (변경 없음) | 2.2 초 |
| 검색 | 0.4 초 |
| 첫 토큰 | 12 ~ 15 초 |
| 생성 | 18 ~ 42 초 |

**dev-01 은 병목이 아니다.** 임베딩도 생성도 맥북 Ollama 로 나가기 때문에
여기서 도는 것은 파일 순회·청킹·HTTP 대기뿐이다. 전체 인덱싱 61 초 중
dev-01 이 실제로 쓴 CPU 는 6.2 초고 나머지 55 초는 응답을 기다린 시간이다.
메모리도 HNSW 가 910×1024 차원이라 4MB 수준이라, 4GB 상한에서 제일 큰
항목은 오히려 langchain 임포트다.

**첫 토큰 12~15 초는 프롬프트 평가 시간이고 모델 적재와는 별개다.** 예전에
이 표에 "0.8 초 (모델이 올라와 있을 때)" 라고 적혀 있었는데, 그건 같은
질문을 두 번 던져 Ollama 프롬프트 캐시에 맞은 값이었다. 새 질문은 컨텍스트
3~5 천 자를 매번 평가해야 해서 12 초 아래로 내려가지 않는다. 캐시에 맞으면
0.2 초에 나오므로 두 값을 섞어 보면 진단이 어긋난다.

Ollama 는 5 분 놀면 모델을 메모리에서 내린다. 14b 는 9GB 라 다시 올리는
데만 14 초가 더 붙는데, `query.py` 가 `keep_alive=30m` 을 보내 이걸
막는다.

  레지스트리가 있어 탐나지만 같은 디렉토리에 auth 와 비밀번호 해시가 같이

## Home Assistant

`homelab-ha` 소스는 `~/git_code/homelab/homelab-ha` 를 본다. HA 는 Proxmox VM 위의
Home Assistant OS(vmid 111)라 `/config` 를 WSL 에서 직접 읽을 수 없다.
HA 안에서 `/config` 를 git 레포로 만들어 push 하고, 여기서 clone 해 두면
다른 소스들과 똑같이 다뤄진다(커밋 이력도 `history` 로 들어간다).
레포가 없으면 `collect_docs.py` 가 조용히 건너뛴다.

### 제어에서 RAG 가 맡는 몫

"거실 불 꺼" 한 번에 세 가지가 필요하다. 셋을 서로 다른 것이 담당한다.

| 필요한 것 | 담당 | 이유 |
|---|---|---|
| 무엇을 건드릴지 고르기 | **RAG** | 검색으로 좁히는 문제다 |
| 지금 상태가 어떤지 | HA API | 계속 변한다. 벡터에 넣으면 낡는다 |
| 실제로 끄기 | tool calling | 검색 결과는 실행이 아니다 |

RAG 가 실행을 대신하지는 못하지만, **무엇을 실행할지 고르는 근거는 RAG 가
댄다.** 엔티티가 수십 개를 넘어가면 전부 프롬프트에 넣을 수 없고, 이름만
봐서는 `light.wiz_rgbw_tunable_a1b2` 가 어느 방인지도 알 수 없다. 내
`automations.yaml` 과 `scripts.yaml` 이 코퍼스에 있으면 "취침 모드" 가
실제로 무엇을 끄고 무엇을 남기는지를 근거로 답하고 고를 수 있다.

주의할 것은 **HA Assist 가 이미 일부를 해 준다**는 점이다. Assist 에
노출한 엔티티는 HA 가 알아서 프롬프트에 넣고 tool 로 만들어 준다.
그래서 RAG 가 값을 더하는 지점은 엔티티 목록 자체가 아니라, HA 가 절대
프롬프트에 넣어 주지 않는 것 — 설정의 의도, 자동화의 구조, 왜 이렇게
했는지다. 엔티티 목록은 노출 대상이 프롬프트에 안 들어갈 만큼 많아졌을
때 RAG 로 좁힌다.

최종 형태는 에이전트가 tool 두 개를 드는 것이다. 하나는 이 코퍼스를 치는
검색 tool, 하나는 HA 서비스 호출. 그래서 순서가 litellm → RAG 서비스 →
에이전트다.

## 알려진 제약

2026-08-13 에 거점을 회사 노트북 WSL 에서 dev-01(LXC) 로 옮겼다. 상시
켜져 있는 기계라 "PC 가 켜져 있을 때만 쓸 수 있다" 는 제약은 없어졌다.

남은 것은 **`~/.claude` 22 건이 git 레포가 아니라는 것**이다. 이건
`context` 카테고리 전체이자 이 코퍼스에서 유일하게 원격이 없는 소스라,
dev-01 을 다시 만들면 그만큼이 사라진다. `azure-terraform-standard`
107 건은 원격을 만들어 해결했다.

`homelab-ha` 는 레포는 있지만 비어 있어서 수집이 0 건이고 git log 도
실패한다(커밋이 없다). HA `/config` 를 push 하면 채워진다.

진짜 병목은 여전히 맥북이다. 임베딩도 생성도 거기서 도니 맥북이 자면
dev-01 이 떠 있어도 멈춘다.
